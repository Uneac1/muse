
## 报纸模块系统性收口计划

### Summary
把当前报纸页的 5 个表层问题，统一抽象成 4 类系统性问题，一次性解决：

1. **工作台状态丢失**
   刷新后排序、阅读位置、页面状态回退。
2. **AI 聚合层信息密度不足**
   总编台覆盖不全、重点不够、卡片摘要不稳定。
3. **信源/抓取链路缺少自动恢复**
   Linux.do 只是一个样本，任何 RSS、正文、回复、图片抓取失败都不该靠手动刷新。
4. **阅读链路分层不清**
   列表、阅读、全文抓取、AI 摘要、降级文案互相打架，导致反复出现“摘要模式”“抓不到正文”“返回报纸页又重刷”。

目标不是修单点，而是把报纸模块改成一个有状态、有恢复能力、有异步补全能力的 AI 新闻工作台。

### Root-Cause Model
后续实现统一按下面 4 类故障模型收口，不再按站点单修：

#### A. Source-level failures
适用范围：
- RSS 拉取失败
- Linux.do / GitHub / 任意信源失联
- 某个来源短时超时或被限流

统一处理：
- 每个 source 都有独立状态机：
  `ok | stale | failed | recovering`
- 每个 source 都记录：
  最近成功时间
  最近失败时间
  最近错误原因
  下次重试时间
- 报纸页加载时：
  优先展示最新可用缓存
  后台自动重试失败源
- 恢复成功后：
  只刷新对应 section，不整页硬刷新
- 失败展示文案统一成“自动恢复中”，不再只显示 `失败源：xxx`

这条不是只给 Linux.do，用在全部 source。

#### B. Detail-level failures
适用范围：
- 正文抓不到
- 图片抓不到
- 回复抓不到
- 可读正文提取失败
- 某些站点正文慢或结构差

统一处理：
- 阅读详情拆成多路异步子任务：
  `meta`
  `fulltext`
  `images`
  `replies`
  `translation`
- 每一路都有自己的状态：
  `pending | partial | ready | failed | recovering`
- 详情接口不再用“整包成功/整包失败”的方式返回
- 前端按子模块状态渲染：
  正文没到，不影响图片和回复先显示
  回复没到，不影响正文先读
  翻译没到，不影响原文先看
- “暂时未能抓取正文，当前先展示摘要模式。” 这类总降级文案删除，改为模块化状态提示：
  正文继续补抓中
  图片继续补抓中
  评论继续补抓中

这条不是只修某一篇文章，而是把所有详情失败统一纳入子任务状态机。

#### C. AI generation failures
适用范围：
- 列表卡片摘要没出来
- AI 总编台内容太少
- 文章 AI 导读超时
- 某个 AI 账号临时不可用

统一处理：
- AI 任务按层分开：
  列表卡片 AI
  总编台 AI
  阅读页文章 AI
- 每层 AI 都有独立状态和缓存：
  `pending | ready | failed | retrying`
- AI 失败不再永久 pending
- AI 任务有统一重试策略：
  首次失败后短退避
  账号池切换
  降级 provider / 模型
  达到阈值后显式 failed
- 总编台生成策略改成：
  先分领域生成
  再做全局汇总
  不是一口气吃完整份报纸再指望一次成功
- highlights 强制补满，不再因为部分 AI 结果缺失只剩 4 条

这条不是只优化“AI 总编台”，而是把整个报纸页 AI 统一成可恢复任务系统。

#### D. Workspace-state failures
适用范围：
- 手动排序刷新丢失
- 回到报纸页又重刷
- 阅读跳转后上下文丢失
- 搜索/排序/滚动位丢失

统一处理：
- 报纸页变成真正的工作台状态容器
- 本地持久化统一存：
  领域排序模式
  领域手动顺序
  文章排序模式
  搜索词
  当前打开文章
  阅读抽屉开关
  滚动位置
  当前已拿到的 AI 总编台数据时间戳
- 返回报纸页时优先恢复本地工作台状态，再决定是否后台刷新
- 阅读入口改成右侧抽屉，避免整页路由跳转导致状态丢失

这条不是只修“排序刷新回初始”，而是把整个报纸页做成状态保持型界面。

### Implementation Changes
#### 1. 报纸页改造成状态型工作台
- 把当前页面状态持久化从“只存手动顺序”升级成完整 `newspaperWorkspaceState`
- 手动排序区块改成轻量折叠控制器：
  默认只显示当前排序摘要 + 展开按钮
  展开后显示紧凑拖拽列表
  列表用单行 chip/row，不再是大卡片
- 阅读入口切到右侧抽屉
- 抽屉关闭时恢复原滚动位和原筛选上下文
- `/newspaper/read` 保留兼容，但主入口不再依赖它

#### 2. 总编台改成高占比全域聚合
- 总编台放到报纸页主视觉区，不再是轻量附属模块
- 结构固定为：
  全局标题
  全局摘要
  10 条重点
  风险观察
  跟进方向
  全领域分区摘要矩阵
- 总编台默认覆盖全部 section，不依赖当前筛选
- 如果用户搜索，另做“当前视图摘要”次级块，而不是缩掉全局块
- highlights 生成规则改成：
  先确保每个非空领域至少 1 条
  再按分数补齐到 10 条

#### 3. 统一自动恢复框架
- 为所有 source 增加 source-level 状态机和后台重试
- 为所有 article detail 子模块增加 detail-level 状态机和后台补抓
- 为所有 AI 任务增加 ai-task 状态机和重试队列
- 所有自动恢复统一走后台，不靠用户刷新按钮触发
- 刷新按钮只保留成“强制立即同步”，不是唯一恢复方式

#### 4. 全文抓取改成分层抓取器
- 全文抓取拆成至少三层：
  原站 HTML 抽取
  元信息/摘要/可读性提取
  备用抓取器/二次补抓
- 列表卡片 AI 只走轻量正文摘录，不走重型全文翻译链
- 阅读页才启用重型详情链路
- 对慢站增加硬超时与任务分离，避免拖垮首页
- 抓不到正文时不直接结束，而是进入 `recovering`，后台继续补抓

### Public Interfaces / Types
需要把接口从“最终结果型”改成“状态可观察型”：

- `NewspaperSourceStatus`
  新增 `lastSuccessAt`
  新增 `lastFailureAt`
  新增 `nextRetryAt`
  `status` 扩展为 `ok | stale | failed | recovering`

- `NewspaperArticle`
  保留 `aiCardStatus`
  新增 `readerStateKey`
  新增 `detailStatus`
  `detailStatus` 建议为 `partial | ready | recovering | failed`

- `NewspaperArticleDetail`
  新增模块级状态：
  `fulltextStatus`
  `imageStatus`
  `replyStatus`
  `translationStatus`
- 不再用单一“摘要模式”覆盖整篇文章状态

- `NewspaperBriefingAiInsight`
  保证固定包含：
  `headline`
  `summary`
  `highlights[10]`
  `watchlist`
  `opportunities`
  `sections[]`
  可选 `coverage` 字段说明覆盖了哪些领域

### Test Plan
#### 工作台状态
- 手动排序后刷新页面，顺序和“手动模式”都保留
- 打开阅读抽屉后关闭，搜索词/排序/滚动位不变
- 页面自动刷新后不重置工作台状态

#### 自动恢复
- 任意 source 失败后自动进入 `recovering`
- 后台重试成功后对应 section 自动恢复
- Linux.do 只是其中一条验证样本，不单独特判为唯一测试对象

#### AI 聚合
- 总编台在 8 个领域都有内容时能稳定给出 10 条重点
- 某些领域为空时，仍能输出完整总编台，不缩成 4 条
- AI 卡片失败后状态变 `failed`，不是永远 pending
- AI 卡片在后台恢复后能自动刷新到页面

#### 阅读链路
- 正文抓取失败时页面显示模块状态，而不是整篇“摘要模式”
- 正文后续补抓成功后自动切换到完整阅读状态
- 图片/回复/翻译任一路失败不影响其余模块显示

#### 回归
- `server` build
- `web` build
- `smoke:newspaper`
- 新增两类 smoke：
  source auto-recovery smoke
  workspace state restore smoke

### Assumptions / Defaults
- 阅读主入口采用右侧抽屉。
- 总编台默认始终展示“全领域总览”，不随搜索词缩小。
- 自动恢复对所有 source/detail/AI 任务统一生效，不做 Linux.do 单点修补方案。
- 抓不到正文时默认继续后台补抓，而不是把摘要模式当最终交付。


## 报纸正文抓取失败根因修复计划

### Summary
这次不是做“诚实语义”，而是直接修正文抓取链。现场取证已经确认有两条真根因：

- 普通网页链路不是单纯抓不到，而是 `抓 HTML -> 提正文 -> 翻标题/摘要/整篇正文 -> 抓评论` 被绑进同一个 `18s` 总超时里。实测一篇 YC 页面：抓 HTML `2.4s`、提正文 `0.1s`，但翻标题 `6.8s`、翻摘要 `5.4s`、翻整篇 `38.9s`，总计 `53.7s`，必然超时回落到 fallback。
- `extractReadableContent` 当前对不少页面会把导航、页头、站点噪音当正文，导致即使抓到 HTML，提出来的也不是有效正文。
- `Linux.do` 直抓 HTML 本身也不稳，当前会在 `fetchArticleHtml` 这一步超时，导致直接回落。

已锁定修法为“正文优先”：先稳定拿到正文原文，翻译和评论异步补全，不再因为翻译慢把正文整条链拖死。

### Key Changes
#### 1. 正文链路拆成两阶段
- `getArticleDetail` 改成“正文主链”和“增强链”分离。
- 主链只负责：
  - 抓 HTML
  - 提标题 / 摘要 / 正文原文
  - 提图片
  - 返回首屏可读内容
- 增强链异步负责：
  - 整篇正文翻译
  - 评论抓取与翻译
  - 二次补全摘要
- 主链单独超时，目标是保证正文首开稳定；增强链失败不再把 `fulltextStatus` 一起拖回 `recovering`。

#### 2. 状态语义按真实能力拆开
- `fulltextStatus` 只反映“正文原文是否真实拿到”，不再因为翻译或评论失败一起变成 `recovering`。
- `translationStatus` 和 `replyStatus` 独立失败、独立恢复。
- fallback 仅在“连 HTML / 正文原文都拿不到”时使用；如果正文原文已拿到，就必须返回真实正文，即使翻译为空。

#### 3. 正文提取器去噪
- 收紧 `extractReadableContent` 的候选优先级，优先真正文章容器，降低 `body/main` 整块兜底权重。
- 新增正文质量判定：
  - 若提取结果命中大量导航/菜单/站点壳文案，判定为低质量正文。
  - 低质量时继续尝试更窄的候选块，而不是直接接受脏正文。
- 对明显站点壳词做统一去噪，避免把菜单、页脚、营销模块当正文。

#### 4. Linux.do 走专用正文路径
- `Linux.do` 不再优先走通用 HTML 正文提取。
- 直接基于 topic JSON 构建正文和回复：
  - 首帖作为正文主内容
  - 后续楼层作为评论
  - 仅在 topic JSON 拿不到时再尝试 HTML
- 这样可以绕开 Linux.do 页面直抓不稳和 HTML 壳层噪音问题。

#### 5. 后台补全与缓存策略重排
- 首次命中正文后立即缓存正文版本，不等翻译完成。
- 异步补全成功后覆盖缓存中的 `translatedContent` / `replies` / `statusMessage`。
- `scheduleDetailRetry` 只对“正文未拿到”或“Linux.do 专用接口失败”触发；不再对“仅翻译未完成”反复整条重抓。
- 保留短时间重试，但避免当前这种“每次读取又重新打一整套慢流水线”。

### Public Interfaces / Data Shape
- 不新增前端接口。
- 保持 `GET /api/newspaper/article` 返回结构不变，但状态语义调整：
  - `fulltextStatus`：只表示正文原文
  - `translationStatus`：只表示中文正文
  - `replyStatus`：只表示讨论区
- 允许 `originalContent` 已完整、`translatedContent` 为空或部分完成，这应被视为正常首屏结果，而不是失败态。

### Test Plan
- 正文优先验证
  - 对普通网页样本，`originalContent` 能在主链超时内返回，且不是 seed title + seed summary 拼接。
  - 当翻译慢时，`fulltextStatus` 应为 `ready`，`translationStatus` 可为 `pending/recovering/partial`。
- 去噪验证
  - YC 这类页面不再把导航菜单当正文开头。
  - 提取结果前几段应为正文主体，而不是 `Open menu / About / Apply / FAQ` 之类站点壳。
- Linux.do 验证
  - 真实 Linux.do topic URL 能返回首帖正文。
  - 回复区优先来自 topic JSON，不依赖 HTML 评论探测。
- 回退验证
  - 仅当 HTML/正文原文都拿不到时，才返回 fallback 详情。
  - 不允许“正文已拿到，但因为翻译慢又退回 fallback”。
- 回归验证
  - `npm run build`
  - `npm run verify:ui`
  - `npm run verify:core`
  - 额外加一条服务侧验证：直接调用 `getArticleDetail` 检查普通网页与 Linux.do 样本的状态组合和正文长度。

### Assumptions
- 默认采用“正文优先”，首屏先保证原文可读，中文翻译和评论允许稍后补齐。
- 不新增新页面交互，本轮重点在后端抓取管线与状态判定。
- `Linux.do` 被视为特殊源，允许专用正文/评论抓取逻辑，不强行复用通用 HTML 提取链。
