# Muse Dashboard / Inbox UX 优化交付

## 适用范围
- `web/src/pages/Dashboard.tsx`
- `web/src/pages/Inbox.tsx`

## 当前问题
- `Dashboard` 首屏有两排统计卡，主任务不明确，进入后先看到数字，不知道先处理什么。
- `Dashboard` 的刷新、异常、邮件量、分布图同层竞争，视觉中心过多。
- `Inbox` 顶部说明偏长，邮件列表虽然干净，但缺少“现在有无异常 / 是否有新邮件 / 要不要继续翻页”的判断锚点。
- 两个页面的首屏都偏“展示数据”，不够“驱动动作”。

## 推荐方向
统一成“主任务锚点 + 3 个证据卡 + 内容主区”的结构。

### Dashboard
- 首屏第一块改为“今日系统状态卡”：
  - 主标题：现在是否需要处理异常
  - 辅助说明：异常账户数、待刷新 token、在线代理
  - 主按钮：去处理异常
  - 次按钮：刷新数据
- 原先 8 张统计卡压缩为 3 张证据卡：
  - 邮箱健康
  - 代理健康
  - 缓存邮件量
- `QuickActions` 保留，但降级到第二屏左侧。
- `RecentMails` 作为第二屏右侧主内容，保留“最近发生了什么”的价值。
- 各类分布图继续保留，但统一移到下方“诊断区”，避免抢首屏焦点。

### Inbox
- Hero 区压缩成一句话：统一收件箱，只看最新邮件与处理线索。
- 顶部统计从 3 张卡改为：
  - 新近邮件数
  - 覆盖账号数
  - 最近同步时间
- 在邮件列表前增加一个“处理提示条”：
  - 有新邮件时提示“优先看前 10 封”
  - 有错误时直接展示错误和重试
- 邮件卡结构固定为：
  - 第一行：主题 + 时间
  - 第二行：发件人 / 账号 / 邮箱夹
  - 第三行：正文预览
  - 第四行：展开 / 收件人
- 收起态正文建议最多 2 行，不要 3 行，提升列表扫描效率。

## 组件规则

### 主任务卡
- 大圆角，浅边框，白底
- 一块卡里只允许一个高强调按钮
- 标题和状态必须在 3 秒内看懂

### 证据卡
- 统一高度
- 只保留一个主数字和一条解释
- 不放超过 1 个动作

### 列表卡
- 卡内信息固定四层，不随页面变化
- 时间永远右上对齐
- 次要信息统一 `text-sm text-muted-foreground`

## 视觉建议
- 首屏减少蓝紫渐变使用频率，改为更稳的白底 + 极浅色状态底。
- `danger` 用在异常账户与错误提示，其他数字不要无意义上色。
- Dashboard 的彩色统计卡建议降饱和，避免看起来像独立模块集合。

## fullstack 落地顺序
1. 先重组 `Dashboard` 首屏信息层级。
2. 再压缩 `Inbox` hero 和统计卡。
3. 最后统一卡片高度、按钮样式、列表节奏。

## 验收口径
- 打开 `Dashboard` 后第一眼能知道要不要处理异常。
- 打开 `Inbox` 后第一眼能知道最近是否有新邮件和是否需要继续下翻。
- 两页首屏都只保留一个真正的视觉中心。
